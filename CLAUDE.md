# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Workflow

- **Start every new task in a fresh worktree when you're on `main`.** Before touching anything, check the current branch. If it's `main`, do NOT work on it directly — create a new git worktree on its own branch for the task and do all the work there. Only skip this if the user has already put you on a task branch/worktree or explicitly says to work on the current branch.
- **On a non-`main` branch, push each commit before testing/running it locally — once past the first iteration.** The first commit that opens the PR still runs local tests first, same as always. After that PR exists, later commits on the same branch: commit, push immediately, and only then run tests/verification locally — don't hold a commit back to test it first. The one exception is a rebase that hit conflicts — resolve those and confirm tests pass locally before pushing, since a bad rebase resolution is a correctness risk, not just a normal iteration.
- **Every PR must be linked to an issue in `ARTPARK-SAHAI-ORG/calibrate-frontend`.** All issues live in that repo, not this one. Before opening a PR, search it for an existing issue covering the work (`gh issue list --repo ARTPARK-SAHAI-ORG/calibrate-frontend --search "<keywords>" --state open`). If one fits, use it. If none does, create one (`gh issue create --repo ARTPARK-SAHAI-ORG/calibrate-frontend`) describing the problem the PR solves. Then start the PR description with the cross-repo closing line on its own first line, before anything else: `Fixes ARTPARK-SAHAI-ORG/calibrate-frontend#<number>`. A bare `Fixes #<number>` would point at a nonexistent issue in this repo, so always write the full `owner/repo#number` form.
- **Before any change or new feature, do this first — every time.** Whenever you're asked to make a change, add a feature, or modify anything:
  1. **Review the existing code thoroughly** for code/functionality that already does (or partly does) what's being asked — don't build on an empty assumption.
  2. **Make a plan** that splits the work into independent subtasks, then run the `parallelize` skill to execute the disjoint ones in parallel (see "Parallel execution" below — the skill is mandatory, not optional).
  3. **Identify code to reuse or repackage** into shared, reusable functions to support what needs to be built, rather than duplicating logic.
  4. **Prefer well-known, reliable libraries** over re-implementing functionality that already exists in one — unless the requirements genuinely demand a custom solution.
  5. **Share the plan and ask** about any choices that need to be made, laying out the tradeoffs, instead of making assumptions on the user's behalf.
  6. **Add as few comments as possible** — see the "Comment sparingly" rule below. A small change usually needs none; don't reach for a comment to explain each edit.
- **When adding or editing an API endpoint, ask whether it should be public — unless it already is.** Any time you create a new route or change an existing one, check whether it already carries `tags=["Public API"]` (see the "Public API docs are tag-gated" fact). If it does, leave it public. If it does NOT, ask the user whether to expose it on the unauthenticated public API page (which also means wiring it to `get_org_jwt_or_api_key` so API-key clients can call it) or keep it JWT-only — lay out the tradeoff, don't decide silently. Never publish a route by adding the tag without explicit confirmation.
- **When adding or editing a route, follow the `api-writing-style` skill for its docs.** Every endpoint gets an explicit imperative `summary=`, a concise verb-first docstring, and `Field`/`Path`/`Query` descriptions on all params and request/response models. The full house style (verb vocabulary, shape hints, per-endpoint checklist) lives in [.cursor/skills/api-writing-style/SKILL.md](.cursor/skills/api-writing-style/SKILL.md) — read it before documenting routes. Enforced by [tests/test_api_docs_style.py](tests/test_api_docs_style.py) (also runnable via `uv run python scripts/check_api_docs_style.py`).
- **Before claiming any change that touched a rendered API doc string is done, run the `api-docs-audit` skill.** If the change added or edited a route `summary=`, a route docstring, a Pydantic model class docstring, or any `Field`/`Path`/`Query` `description=` (including factory-generated ones), audit the change with [.cursor/skills/api-docs-audit/SKILL.md](.cursor/skills/api-docs-audit/SKILL.md): it inventories every changed rendered string, verifies each against `api-writing-style` (one sub-agent per string, covering the judgment-call rules the mechanical gate can't), and publishes a field-level HTML report grouped by file then method. This is in addition to `tests/test_api_docs_style.py`, not a replacement — the test catches only the machine-checkable subset (em-dashes, semicolons, unit echoes); the audit catches explanatory parentheticals, per-X phrasing, null caveats, enum re-listing, and consistency. Fix every violation it surfaces (generalizing the fix across the surface) and re-run until the report is clean before reporting done.
- **When the Public API surface changes, update client overlays in the same PR — every time.** Adding, removing, or renaming a route tagged `Public API` is not done until **both** naming overlays are updated manually in that change: [fern/openapi-overrides.yml](fern/openapi-overrides.yml) (Fern Python SDK: `x-fern-sdk-group-name` / `x-fern-sdk-method-name`) and [openapi/overlay.yaml](openapi/overlay.yaml) (Speakeasy CLI: `x-speakeasy-group` / `x-speakeasy-name-override`, plus `x-speakeasy-mcp` for MCP tool metadata). Overlays are **not** generated from the spec — Fern and Speakeasy will still emit the new route without them, but with ugly auto-derived names. Run `uv run --group dev pytest tests/test_sdk_overrides.py -q` before claiming done; CI enforces exact parity with `_build_public_openapi()`. Removing a route: delete its entries from **both** files. Renaming a path or HTTP method: update both overlays to match. **Shipped SDK/CLI/MCP binaries auto-publish after every production deploy** (see [SETUP_SDK.md](SETUP_SDK.md)) — backend overlay fixes alone don't reach installed `pip`/`brew`/`npm` users until that deploy + publish cycle runs.
- **Comment sparingly — this is the default, not an aspiration.** Most changes need NO comment. Do not narrate a diff with a comment on every edit. Reserve comments for genuinely significant or non-obvious pieces — a real constraint, tradeoff, or footgun a stranger would trip on. For a small or self-evident change, write **at most one short concise line**, and usually nothing. Never restate what the code plainly says. If more explanation would help, leave it out — the user will ask and you can explain it in chat instead of baking narration into the file. When in doubt, delete the comment.
- **Write code comments per the `code-comments` skill.** Every `#` comment (and internal non-rendered docstring) that survives the sparingness bar above must be standalone and timeless — written for a stranger reading the file cold, never a log of our conversation, the review round, or the edit that produced it. Comment the *why* (constraint, tradeoff, footgun), not the *what*; no "we"/"as discussed"/"previously… now"/"introduced here"; cross-reference by symbol name, not by story; one idea in the fewest words. The full rules and before/after examples live in [.cursor/skills/code-comments/SKILL.md](.cursor/skills/code-comments/SKILL.md). (Rendered API doc strings follow `api-writing-style` instead.)
- **Commit when the work is done — don't wait to be asked.** Once all the required changes for a task are made and the scoped tests pass, create the commit yourself. Use a focused message that explains the *why*. Do not push unless explicitly asked. The standard safety rules still apply: never amend published commits, never skip hooks, never `git add -A` blindly, never commit secrets. **Before committing, re-scan the diff for comments you added and delete the ones that merely narrate the change** — keep only comments that clear the "Comment sparingly" bar.
- **Keep CLAUDE.md in sync with the app's mental model.** After making changes, ask yourself: does this commit shift a *high-level* understanding of the app — a load-bearing invariant, an architectural rule, a convention, a non-obvious gotcha, a new subsystem, or a contract between components? If yes, update CLAUDE.md in the **same commit** so future Claude sessions inherit the new mental model. Don't record routine fixes, file moves, renames, or anything obvious from reading the code — only changes a fresh reader would otherwise miss. When in doubt, prefer updating an existing bullet over adding a new one.

## Parallel execution (default)

**Always invoke the `parallelize` skill before writing any code.** Once the plan is settled and you are ready to implement, run the skill first — every time, whether or not the user asks for it, and whether or not the task looks small. Do not start editing files without it. The only exception is a change confined to a single file with no independent parts; say so in one line and proceed.

The skill splits the work into subtasks, marks which are independent, and runs those as parallel agents, each owning a disjoint set of files/sections so they never edit the same file at once. Dependent subtasks stay sequential. Show the plan before launching.

## Project Summary

Calibrate Backend is a FastAPI REST API that wraps the `calibrate` CLI tool to orchestrate long-running evaluation and simulation jobs:

1. **STT/TTS evaluation** — benchmark speech providers against datasets
2. **LLM agent testing** — unit tests and multi-model benchmarks
3. **Voice/chat simulations** — simulated conversations between AI agents and personas across scenarios

The backend persists state in SQLite, stores artifacts in S3-compatible object storage (or local disk when `OBJECT_STORAGE_MODE=local` for development), and spawns `calibrate-agent` CLI subprocesses (PyPI package `calibrate-agent`, console script `calibrate-agent`) to do the actual work. Authentication is Google OAuth or email/password, gated by JWTs.

## Testing Discipline (load-bearing)

Treat tests as part of the feature, not an afterthought. The rules are non-negotiable:

- **New feature ⇒ new tests.** Any new function, endpoint, router, helper, or branch added to `src/` must ship with tests that exercise it. Mirror the layout: `src/foo.py` → `tests/test_foo.py`; a new router endpoint extends the matching `tests/test_routers_*.py` file. If no test file fits, create one alongside the existing ones — do not bury new behavior inside an unrelated test.
- **Modified feature ⇒ updated tests.** When you change behavior of existing code (bug fix, refactor, semantic change), update or add tests that pin the new behavior. If the existing test still passes after a real behavior change, the test is wrong — fix the test, don't silently lose the assertion.
- **Verify before claiming done — scoped only.** Before reporting any code change as working, run the tests that cover the changed code and confirm they pass. Run ONLY the scoped subset — the specific file (`uv run --group dev pytest tests/test_foo.py -q`) or `-k` selector that hits your change. **Do not run the full suite after every edit during iteration**; full-suite runs are slow and reserved for **once, immediately before pushing / opening the PR**. If a scoped run passes, that is sufficient evidence the change works — type checks and "the diff looks right" are not substitutes, but the full suite is overkill for individual edits.
- **No skipping or weakening tests to make them pass.** If a test fails after your change, the default assumption is the code is wrong, not the test. Only update an assertion when you have explicitly decided the old behavior was incorrect, and say so in the PR description.
- **Background-thread / subprocess code needs a test seam.** Job runners spawn `calibrate` and threads — tests stub `subprocess.Popen` / monkeypatch the runner registry rather than really launching CLI processes. Follow the patterns in `test_run_tasks.py`, `test_job_recovery.py`, and `test_routers_*.py`.
- **Check diff coverage before saying a change is done — every time, not just when CI flags it.** "Tests pass" is not the same as "every new line is covered" — a passing suite says nothing about a branch (an `if`, a guard clause, an error-fallback) that no test ever reached. Before reporting a change complete, run the scoped test file(s) with `--cov=<touched module path> --cov-report=term-missing` and check every line/branch your diff added or changed against the printed "Missing" column. A line number from your diff appearing there means an untested branch — write a test that reaches it (or a direct unit test of the helper, see `test_slim_run_list_helpers_guard_edge_cases` / `test_run_evaluator_names_guards_malformed_snapshot_entries` for the pattern of testing a small pure helper directly with malformed input). Pre-existing gaps unrelated to your diff are not your problem to fix. This is the same check the `codecov/patch` GitHub status makes on the PR — catching it locally means the PR doesn't come back red after you've already said "done."

## Code Layout

All application code lives under `src/` and runs with `src/` as the working directory (see Dockerfile). Imports are flat (`from db import ...`, `from auth_utils import ...`) — there is no package namespace. When you touch a file here, keep comments minimal (see "Comment sparingly") — add one only where the reason for the code isn't obvious.

- `src/main.py` — FastAPI app, lifespan hooks (job recovery on startup), custom HTTP-Basic-auth'd `/docs` routes, Sentry/OTEL setup, router wiring
- `src/db.py` — single-file SQLite layer (~7000 lines). All schema DDL, migrations (wrapped in `try/except sqlite3.OperationalError` — see architecture.md gotcha on `DEFAULT CURRENT_TIMESTAMP`), and CRUD. Soft deletes (`deleted_at IS NULL` filter) everywhere.
- `src/utils.py` — S3 helpers, presigned URLs, `build_tool_configs()`, process-group kill helpers, job-queue registry (`register_job_starter`, `can_start_*_job`, `try_start_queued_*_job`), `TaskStatus` enum, `is_job_timed_out()`, Sentry capture helper
- `src/auth_utils.py` — JWT verification, `get_current_user_id` dependency, `require_superadmin`
- `src/org_scope.py` — shared org-ownership guards (`ensure_owned_agent`, `ensure_owned_evaluator`) used by routers that link evaluators; 404 on cross-org access
- `src/dataset_utils.py` — `resolve_dataset_inputs()` / `inject_dataset_item_ids()` shared by STT and TTS routers
- `src/job_recovery.py` — on startup, kills orphaned process groups and restarts `in_progress` jobs
- `src/llm_judge.py` — `{{variable}}` template rendering, OpenRouter-based judge invocation, and `build_evaluator_cli_payload()` that shapes linked evaluators into the dict sent to the calibrate CLI (STT/TTS/LLM tests/simulations all share this).
- `src/annotation_eval_runner.py` — background worker for annotation-task evaluator runs; routes LLM-judge work through the calibrate CLI's STT `--eval-only` mode so judge logic isn't duplicated.
- `src/annotation_metrics.py` — human-vs-human and human-vs-evaluator agreement metrics for annotation tasks (pairwise mean agreement on shared rows; row-level overall has `evaluator_id=None`).
- `src/routers/` — one file per resource: `auth`, `user_limits`, `datasets`, `personas`, `scenarios`, `agents`, `tools`, `agent_tools`, `tests`, `agent_tests`, `stt`, `tts`, `simulations`, `evaluators`, `annotators`, `annotation_tasks`, `annotation_agreement`, `jobs`, `public`. Each router registers a job starter via `register_job_starter(...)` at module load so `try_start_queued_*_job` can resume queued work. `public.py` bypasses auth by design — its routes are excluded from the auth middleware so anyone with a valid `share_token` can view shared results.

## Architectural Load-Bearing Facts

These are the invariants most likely to trip up an edit. The architecture doc has the full explanation; this is the short form.

- **Three independent job queues**: eval (`stt-eval`, `tts-eval`), agent-test (`llm-unit-test`, `llm-benchmark`), simulation (`text`, `voice`). Each enforces both a global and per-user concurrency limit. Every mutation that completes/deletes/aborts a job must call `try_start_queued_*_job(...)` for that queue — otherwise queued work stalls.
- **User scoping is mandatory**: every DB call takes `user_id`, and routers always raise 404 (not 403) on access-denied to avoid leaking existence. The one exception is applied centrally, never per-router: when the caller turns out to be a member of the owning workspace, the handler below rewrites that 404 into a 403 (nothing is leaked — they can already see the resource). `user_id` on `agent_test_jobs` / `simulation_jobs` is derived by JOIN through the parent entity.
- **A resource in another of the caller's workspaces answers 403 with an `organization_uuid` hint — produced centrally, never per-router.** A shared link (`/agents/<uuid>`) opens with whatever workspace the recipient had active, so a resource they *can* see is still denied under the wrong `X-Org-UUID`. That is a permission problem, not a missing resource: the response is 403 with `detail` "This resource belongs to a different workspace" and the owning `organization_uuid`, so the frontend can switch and retry instead of showing a dead end. Everyone else keeps the plain 404. One handler does it for every route: `_not_found_handler` in [main.py](src/main.py) intercepts any 404, pulls each uuid-shaped segment out of the request path, and calls `find_member_org_for_resource` ([db.py](src/db.py)) — a single UNION over the org-owning tables (direct `org_uuid` column, or a JOIN to the parent for `agent_test_jobs`/`simulation_jobs`/annotation items+jobs/`evaluator_runs`) with the `organization_members` membership join **inside the same statement**, so a non-member can never be told the resource exists. Adding a new org-scoped table means adding one line to `_RESOURCE_ORG_SELECTS`; routers need no change. Three deliberate suppressions, each leaving the plain 404 in place: JWT callers only (an API key is bound to one org), nothing when the resolved org is the caller's *active* org (a parent uuid in the path would otherwise cause a switch-and-retry loop that hides the real 404), and any exception in the lookup degrades to the plain 404 (an exception raised inside an exception handler bypasses Starlette's error middleware and becomes a bare 500). Non-404s pass through FastAPI's default `http_exception_handler` untouched.
- **SQLite stores UTC**; use `datetime.utcnow()` when comparing against `CURRENT_TIMESTAMP` columns. Never `datetime.now()`.
- **Production traces are a normal table in `pense.db`, shipped as a deliberately small first surface.** The `traces` table is created in `init_db()`; storage functions (`create_trace`, `create_trace_with_eval_run`, `get_trace`, `get_traces_by_uuids`, `count_live_traces`, `list_traces`, `soft_delete_traces`) live at the end of `db.py`. Five endpoints only: `POST /traces` (ingest, `get_org_jwt_or_api_key`, tagged `Public API` so the generated SDK/CLI/MCP clients can send traces — both overlay files carry it), and JWT-only `GET /traces` (paginated, optional `agent_id` filter and `q` text search), `GET /traces/{uuid}`, `POST /traces/bulk-delete` (`{trace_ids}`), `POST /traces/convert-to-tests`. **Both bulk endpoints take the same `select_all` toggle the annotation-task bulk actions do**: `{select_all: true, agent_id?, q?, output_type?}` acts on every live trace matching those filters (honoured exactly as `GET /traces` honours them) and ignores `trace_ids`; `select_all=false` (default) requires `trace_ids` non-empty (422 otherwise). Delete resolves in one SQL UPDATE over the filter (`db.soft_delete_traces_matching`, no uuid list, no chunking); convert still fetches rows and 400s when more than `MAX_CONVERT_TRACES` match, so a large set converts in filtered batches. **The conversion has shipped**: one test per trace, up to 500 per request, JWT-only and deliberately NOT tagged `Public API`, so neither SDK overlay file changes. `config.history` is the trace's `input` verbatim; for `tool_call` the recorded calls become the expected assertion, and for `response` the recorded reply is dropped because the agent is re-run. Test name is `message_id`, or the trace uuid when that is null, with ` (2)` style suffixes on collision so converting the same traces twice succeeds. Each test links to the agent that produced its trace, and a deleted agent skips the link rather than failing the batch. Linked evaluators must have no `{{placeholder}}` variables (400) since a conversion has no per-test place to supply values; no live version is likewise 400. `tool_call` rejects evaluators outright (400) because the runner never reads them for that row type. **Still cut** and parked on branch `traces-convert-to-tests-parked` (full version at commit e844ea7): a `conversation_id` filter, delete-everything-matching, and a per-workspace configurable cap. Do not re-add these without a reason. **`message_id` and `conversation_id` are pure labels** — nullable, stored, displayed, read by nothing. They were once the idempotency key, which made a customer's ID load-bearing: reusing one for a different turn returned the stored trace and silently discarded the new one. Ingest now always inserts, there is no unique index and no `created` flag, so a retry stores a visible, deletable duplicate instead of losing a turn. Do not re-attach logic to either field. Every trace carries a required `agent_id`, guarded at ingest by `ensure_owned_agent` (404 on unknown or cross-org, checked before the cap so a bad agent never surfaces as a 429), and accepted as an optional list filter. The cap is a module constant `MAX_TRACES_PER_WORKSPACE` in `routers/traces.py` (from `DEFAULT_MAX_TRACES`, default 50000), NOT a per-workspace setting; 429 past it. Count and insert are separate statements, so it can overshoot slightly — a guardrail, not an invariant. Indexes: `idx_traces_org_agent_active` on `(org_uuid, agent_id, deleted_at)` and `idx_traces_org_created` on `(org_uuid, deleted_at, created_at DESC, id DESC)` so a list page neither scans nor sorts the whole workspace. **Trace scoring schema (tables only, not yet wired):** `trace_evaluations` is one durable run per scoring attempt (`pending|processing|completed|failed|skipped`); `ux_trace_eval_active` allows at most one open run per trace. `trace_scores` is one row per `(run_uuid, evaluator_uuid)` with typed `match` (binary) / `score` (rating) columns (CHECK: exactly one) and `evaluator_version_id` NOT NULL — a same-version rescore is a distinct run and does not overwrite earlier history. `agents.auto_score_traces` defaults to 0 (guarded `ALTER`) and is set via `PUT /agents/{uuid}`; the off→on flip 422s when no linked evaluator is eligible (`conversation` → `response`/`llm`, `general` → `general`/`llm-general`; live version; no variables). An already-on agent whose evaluators later all become ineligible stays on. JWT-only `GET /agents/{uuid}/trace-scoring-eligibility` returns that partition (`wrong_type_for_agent` | `no_live_version` | `declares_variables`). Disabling deletes `pending` runs only. `POST /traces` (`ingest_trace`) calls `create_trace_with_eval_run`: if `auto_score_traces` is on it resolves `trace_scoring.resolve_scoring_plan` **outside** the write lock, then inserts the trace and its `trace_evaluations` run in one `BEGIN IMMEDIATE` (the first in this codebase — a deferred `BEGIN` can raise `SQLITE_BUSY` without honouring `busy_timeout`). A runnable run is born `pending` with a non-NULL `criteria` snapshot (`{type, evaluators: [{evaluator_uuid, evaluator_version_id}, ...]}`); eligibility drift or an unknown `interaction_type` writes a visible `skipped` run (`no_usable_evaluators` / `unsupported_interaction_type`) instead of dropping silently. Opted-out agents (the default) insert the trace only. `create_trace` is unchanged and still does not create a run. No worker pool yet. `input`/`output`/`metadata` are JSON stored as TEXT. The ingest contract mirrors test creation on purpose — `input` is `tests.config.history` verbatim (OpenAI format, extras preserved), `output.tool_calls` is the flat `{tool, arguments}` expected-tool-call shape — so the conversion needs no transformation. Each tool call also accepts an optional `output` (the tool's own result, free-form JSON) that is stored and displayed but never converted, since a `tool_call` test asserts the call, not its result. `q` is a case-insensitive substring match, run in SQL over `message_id`, `conversation_id`, and the raw JSON text of `input`/`output`/`metadata`, so it also matches JSON keys and quoting; `%`/`_` are escaped to literals. No index covers it, so it is a full scan of the workspace's live traces. The list endpoint filters and counts **in SQL**: adopt `pagination.py`'s envelope and param names only, never its post-fetch `.apply()` helpers.
- **Subprocesses**: always start with `start_new_session=True`; store `pid`/`pgid` in job details; kill via `os.killpg` SIGTERM→SIGKILL (catch both `ProcessLookupError` and `PermissionError` on macOS). Agent test jobs are the exception — they block on `process.wait()` and do not track PIDs because `agent_test_jobs` has no `details` column.
- **Polling loops that spawn `calibrate`**: redirect stdout/stderr to temp files (not pipes) to avoid buffer-full deadlocks; poll every 2s; only `update_job` when state actually changes (to preserve `updated_at` for the 5-minute timeout check); read intermediate outputs from disk.
- **Simulation abort**: check `_is_job_aborted(task_id)` at every layer (inside polling loop, inside intermediate-update writer, after loop exit, inside `run_simulation_task`, and all exception handlers). Missing any one re-opens a race where the monitoring thread overwrites the abort state.
- **STT/TTS intermediate results are disk-only** during `in_progress` — error/timeout handlers must call `_collect_intermediate_results()` / `_collect_tts_intermediate_results()` before writing failure to DB, or successful providers' data is lost. Timeout handlers must **merge** (not overwrite) with existing DB `success: true` entries.
- **Artifact storage mode**: production/default is `OBJECT_STORAGE_MODE=s3`, where `S3_OUTPUT_BUCKET` is required and presigned URLs are generated on-the-fly from stored S3 keys — never persist presigned URLs in the DB (they expire). Local development can set `OBJECT_STORAGE_MODE=local`; `get_s3_output_config()` returns the sentinel bucket `local-dev-artifacts`, `get_s3_client()` returns `None`, and the storage helpers route to `LOCAL_ARTIFACT_ROOT` instead of AWS — `upload_file_to_s3`/`download_file_from_s3`/`list_object_keys` all branch on `is_local_object_storage()`, so job runners must go through them rather than calling `s3.download_file`/`s3.get_paginator` on the (now `None`) client directly. `/local-artifacts/{key}` acts as the development upload/download URL (`LOCAL_ARTIFACT_BASE_URL` makes generated upload **and** download URLs absolute for the frontend — both `generate_presigned_upload_url` and `generate_presigned_download_url` read the env var, with no per-request base-URL fallback). - **Annotation-task evaluator order is explicit, stored on the pivot.** `annotation_task_evaluators.position` drives every UI surface that lists a task's evaluators (task detail, `/evaluators` detail-shape endpoint, `/summary`, `/agreement`, per-item editor, annotator labelling job). New links append (`MAX(position)+1` among active rows); restore-on-relink also moves to the end. `reorder_evaluators_for_annotation_task` / `PUT /annotation-tasks/{uuid}/evaluators/order` re-numbers atomically and rejects sets that don't match the active linked set. `set_evaluators_for_annotation_task` / `PUT /annotation-tasks/{uuid}/evaluators` is the superset: it reconciles membership (links new, unlinks omitted) AND sets `position` to the given list order in one atomic call (so it does not require the target to match the current set), returning `{linked, unlinked}`. It's the Public API surface for task↔evaluator association, accepts an API key, rejects duplicate ids (400), and validates the whole set before mutating. There is no one-at-a-time link `POST`. Job snapshots are FROZEN: `create_annotation_job` copies the task's position-ordered list into `annotation_job_evaluators.position`, and later reordering on the task does NOT propagate to existing jobs. The labelling form's own settings freeze the same way: `annotation_jobs.comments_enabled` (default 1) and `reasoning_mode` (`optional`/`required`/`hidden`, default `optional`) are set per job by `POST /annotation-tasks/{uuid}/jobs` and returned inside the `job` object on both public labelling routes; the backend stores and reports them, it does not enforce `required` on annotation upsert. Job creation can snapshot a **subset** of the task's linked evaluators: `POST /annotation-tasks/{uuid}/jobs` accepts an optional `evaluator_ids` (validated to be a subset of the task's live links; empty list or unknown id ⇒ 400) that `create_annotation_job` filters the snapshot down to — preserving the task's position order among the chosen ones; omit it (`None`) to snapshot all. The labelling form (`get_evaluators_for_job` → public job payload) shows exactly the snapshotted set, so a subset job shows only those evaluators. Every read path that lists task evaluators MUST `ORDER BY position ASC, id ASC` — anything that forgets it silently falls back to insertion order. **`annotation_task_evaluators.is_optional` rides the same rails as `position`** (0/1, default 0 = required; surfaced as a real bool by `_with_bool_is_optional`): it is snapshotted into `annotation_job_evaluators.is_optional` and frozen there, so flipping it on the task never moves the completion bar under a live job. `PUT …/evaluators` takes it as a separate whole-set `optional_evaluator_ids` (subset of `evaluator_ids`, 400 otherwise) — an id left out is reset to required, and omitting the field entirely (`None`) leaves every flag untouched. Restore-on-relink resets the flag rather than restoring what it carried before. **Auto-completion measures REQUIRED slots only** — `get_evaluator_ids_for_job(job, required_only=True)` — plus a second condition that every item carry at least one judgement, which is what stops an all-optional job from completing on the annotator's first save. Both completion sites (`upsert_public_annotations` in [public.py](src/routers/public.py), the initial-annotations path in `bulk_create_items`) must apply both halves; the snapshot-mismatch gate above the latter deliberately still measures against the FULL snapshot.
- **Agent↔evaluator links use an unordered pivot.** `agent_evaluators (agent_id, evaluator_id, created_at, deleted_at)` mirrors `agent_tests` / `test_evaluators` soft-delete semantics: `add_evaluator_to_agent` inserts, restores soft-deleted rows on re-link, and is idempotent on an already-active link (no 500); `delete_agent` cascades soft-delete to the pivot; agent duplicate copies active links. Public API: `GET /agents/{uuid}/evaluators` (paginated slim `EvaluatorResponse`) and `POST …/evaluators` (link one or more: `{evaluator_ids: [...]}`, additive — skips already-linked, returns `{linked, already_linked}`); JWT-only: `DELETE` unlink one (removal stays off the key API). There is no set-replace PUT — additions go through `POST`, removals through `DELETE`. The `POST` accepts an API key, validates each id as exactly 36 chars (`EvaluatorUuid` in [utils.py](src/utils.py) — malformed ids 422 before DB lookup) and validates the whole set up front (bad id 404, nothing linked). Ownership checks go through [org_scope.py](src/org_scope.py) (`ensure_owned_agent` / `ensure_owned_evaluator`, the latter allowing seeded defaults with `org_uuid IS NULL`). **One-time deploy backfill** — when the pivot first ships, `init_db()` copies every evaluator reachable via `agent_tests` → `test_evaluators` onto the agent (`INSERT OR IGNORE … SELECT DISTINCT`). Gated by a `_schema_migrations` flag (`agent_evaluators_from_test_evaluators_v1`), not table existence — so a crash between CREATE and backfill retries on the next `init_db()`, and later runs never undo manual unlinks. Row count for ops logging uses `SELECT changes()` immediately after the insert (not `cursor.rowcount`, which is unreliable on `INSERT…SELECT`). **Every new agent auto-links the org's fork of the default correctness evaluator (`default-llm-next-reply`)** — `create_agent` calls `_link_default_correctness_evaluator`, which forks the org's copy via `_provision_default_evaluators_for_org` first if it doesn't have one yet (same path a new org uses), then links it. This only happens at creation, never on read — an agent a user later unlinks it from stays without it. A one-time deploy backfill (`link_default_correctness_evaluator_to_agents_v1`) did the same for every pre-existing agent that had zero evaluators linked, leaving agents that already had at least one (of any kind) untouched.
- **`agents.interaction_type` gates test↔agent links AND what calibrate POSTs to the agent.** A second, independent classifying column alongside `type` (`agent`/`connection` — how the agent is reached): `interaction_type` is `conversation` (default, back-and-forth) or `general` (one-shot plain input/output, no conversation). `_build_calibrate_config` writes it into the agent-connection config as the top-level key **`agent_type`** next to `agent_url`, which calibrate reads to pick the request body: `conversation` POSTs the exchange so far as `{"messages": [...]}`, `general` POSTs only the latest user text as `{"input": "..."}` (`TextAgentConnection._build_body`; the CLI kwarg is `type=`, the config key is `agent_type`). Omitting the key keeps the `messages` shape, so the value is always written rather than conditionally. **Simulations always send the conversation** — `routers/simulations.py` must NOT grow this key. It also gates the two endpoints that create a test↔agent link — `POST /agent-tests` and `POST /tests/bulk` (when it's given `agent_uuids`): a `general` test can only link to a `general` agent, and `response`/`conversation` tests only to a `conversation` agent (checked all-or-nothing before any link is created in either endpoint, mirroring the existing not-found check in `POST /agent-tests`). **`tool_call` is the one type that spans both**, decided by its config shape rather than its type, so the gate resolves through `required_agent_interaction_type(test_type, config)` in [tests.py](src/routers/tests.py) and never reads `REQUIRED_AGENT_INTERACTION_TYPE_BY_TEST_TYPE` directly: a `tool_call` test storing `input` (a standalone prompt, the same field a `general` test carries) links only to a `general` agent, one storing `history` only to a `conversation` agent. Bulk enforces exactly one of `input`/`conversation_history` per `tool_call` item (422 otherwise) and runs the agent gate over the BUILT configs, after config assembly and before any write. Nothing downstream branches on the shape: `_build_calibrate_config` widens an `input`-shaped `tool_call` test to `history: [{"role": "user", "content": input}]` at CLI handoff, because calibrate's `test_case_history` reads `input` only when `evaluation.type == "general"` and would otherwise KeyError on the missing `history`. The `input` is **copied, not moved** — it stays on the test case, which calibrate ignores for a non-`general` row but which is echoed back as `test_case` on the run result, where it is the only marker that the test was written as one standalone input rather than a conversation (the frontend reads it to draw Input/Output boxes instead of a chat). The widening still applies under `agent_type: general`: calibrate builds the message list first, then takes `messages[-1]["content"]` as the `input` it POSTs, so the one user turn round-trips back to the standalone prompt. `POST /agent-tests/agent/{uuid}/run` does NOT re-check it when called with explicit `test_uuids` — a caller can still run a mismatched test/agent pair by UUID, since the gate is enforced only at link time, not at run time. **Immutable, like `type`, and immutable the same way: absent from `AgentUpdate`, so `PUT /agents` ignores it** (a body carrying only it gets the generic "No fields to update" 400). It was mutable while it was only a link-time label; now that it picks the request body, a flip would strand every linked test and leave `connection_verified` true against a body the agent no longer receives. `db.update_agent` still accepts it, which is why the convert-to-tests link path still checks it. `POST /agent-tests/agent/{uuid}/run` with explicit `test_uuids` DOES now re-check it (400 listing the offending ids) — immutability alone does not close that path, and calibrate gathers test cases without `return_exceptions`, so one test the agent cannot be sent aborts the entire run rather than failing alone.
- **`evaluator_runs` rows land while an annotation eval job is still `in_progress`, and are provisional until it finishes.** `annotation_eval_runner._run_job` reads calibrate's results files on the same 2-second poll tick that already drives the no-progress watchdog, and stores each score as calibrate writes it (`_store_scored_runs`), so `GET /annotation-tasks/{uuid}/evaluator-runs/{job_uuid}` shows finished items mid-run. Three rules make that safe and MUST hold for any new reader or writer. (1) **Mid-run reads are provisional.** A results file caught mid-append can lose whole trailing fields (`csv.DictReader` leaves them `None`, vs `""` for a present-but-empty cell) — only the LAST row can be cut, so `_read_results_csv` and `_parse_results_simulation` drop just that row. A cut *inside* the last column is undetectable (it reads as a complete row with truncated reasoning), so on success `_run_job` calls `clear_evaluator_runs_for_job` and rewrites every row from the finished files; the complete file is the only authority. (2) **A failed run stores nothing.** Both failure handlers call `_discard_partial_runs` — the task-wide readers (`/summary` run counts, `/agreement`, the `annotation-agreement` trend, the `has_agreement` flag) do NOT filter on job status, so surviving rows would fold a crashed run's first N items into the task's numbers as a real result. (3) **Dedupe is in memory, not in the schema.** `evaluator_runs` has no uniqueness constraint and every tick re-parses the whole file, so a `(item_id, evaluator_id)` set gates the writes; keys are recorded only AFTER the write lands so a failed write retries next tick. Storing does not begin until calibrate has written its `config.json` — its `evaluators_map` is the authority for which column belongs to which evaluator, and the display-name fallback could otherwise pin a score to the wrong one. **Write order is therefore part of the CLI contract**: the real CLI writes `config.json` before any results file and [fake_calibrate_agent.py](src/testing/fake_calibrate_agent.py) mirrors that — a handler that writes it last silently disables in-flight storing under `FAKE_AI_PROVIDERS=1`. How each task type produces incremental output differs (calibrate-agent 0.0.70; `judges.PartialResultsWriter`): `stt`/`tts`/`llm-general` append one `results.csv` row per judged item and flush, in **judge-completion order, not dataset order** — key rows by `id`, never by position. `stt`'s partial header is NARROWER than its final one (`wer`/`cer`/`ttfs`/Sarvam columns only appear in the end-of-run rewrite), which is harmless because the parsers iterate `evaluators_map` columns rather than the whole header. `llm` truncates and rewrites the whole `results.json` array after every item with no atomic replace, so a read landing inside a rewrite hits invalid JSON — `_parse_results_llm` already returns `[]` and the next tick picks it up. `conversation` streams at directory granularity (`row_<i>/` is created BEFORE its `evaluation_results.csv`, so a row dir with no CSV is normal mid-run); its `dataset_map.json` is written up front, so the parser's skip-rows-with-no-map-entry rule can never drop a real row. Each subcommand also fully rewrites its results file at the end of the run, which is a second reason mid-run reads are provisional.
- **Annotation-job soft-delete cascades through reads, not rows.** `soft_delete_annotation_job` only flips `annotation_jobs.deleted_at`. The job's annotation rows are NOT touched. Every annotation read path (`get_annotations_for_task`, `get_annotations_for_item`, `get_annotations_for_slots`, `get_annotations_for_user`, `get_annotations_for_annotator_overlap_slots`, `get_annotated_item_ids`) JOINs on `annotation_jobs` and filters `j.deleted_at IS NULL`, so a soft-deleted job's annotations atomically vanish from list views, inter-annotator agreement, and the human columns of evaluator-run reports. This cascade is intentional and also outlasts the `include_deleted_items=True` reproducibility carve-out used for soft-deleted *items* in eval-run detail — that carve-out preserves item soft-deletes only, never job soft-deletes. Consequence: deleting an `annotation_jobs` row retroactively shrinks the `human_agreement` block of old evaluator runs that referenced it. New annotation reads must keep the same `j.deleted_at IS NULL` filter or they'll leak deleted-job labels into agreement.
- **Default evaluators are per-org editable forks, not shared singletons.** The 12 seeded defaults (`owner_user_id IS NULL` AND `org_uuid IS NULL`, each with a stable `slug`) are **hidden canonical templates** — never returned to an org by `get_all_evaluators` (which now filters `org_uuid = ?`, no `OR org_uuid IS NULL`). Instead every org gets its **own editable/deletable/renameable copy** of each template, forked at org-creation time (`_provision_default_evaluators_for_org`, called from both `create_organization` and `_create_personal_org_for_user`), plus a one-time deploy backfill for pre-existing orgs. **There is no on-read provisioning** — a default added in a later release needs a new one-time backfill to reach existing orgs (the mechanism supports it via the receipt ledger; it just isn't triggered from `GET /evaluators`). A fork carries `owner_user_id` set, `org_uuid` set, `slug=NULL` (the slug is globally `UNIQUE` and stays with the template), and `source_default_slug` for provenance. **The API's `is_default` is derived from `source_default_slug is not None` (OR `owner_user_id IS NULL`), NOT from `owner_user_id` alone — so a fork reads as `is_default` True and the UI groups it under the "Default" tab while it stays fully editable; only from-scratch customs are `is_default` False.** (The `_owner_check` 403 still gates edits on `org_uuid IS NULL` templates, so `is_default` True does not imply read-only.) **`source_default_slug` is surfaced on `EvaluatorResponse`** so clients can still pin a *specific* default by its origin slug (e.g. the FE seeds new tests with `default-llm-next-reply`) — a fork's own `slug` is NULL, so `is_default` alone can't single one out. Idempotency + the **no-resurrection rule** ("a fork the user renamed or deleted is never re-created") ride on a dedicated **receipt ledger** `org_default_evaluators (org_uuid, source_default_slug, evaluator_uuid?, UNIQUE(org_uuid, source_default_slug))` — provisioning forks a slug only when the org has no receipt for it, keying off the ledger, NOT the presence of the forked row. A name collision with an existing custom evaluator skips the fork but still writes a receipt (NULL `evaluator_uuid`) so it isn't retried. A one-time `_schema_migrations`-gated backfill (`fork_default_evaluators_per_org_v1`, `_backfill_fork_default_evaluators`) forks into all pre-existing orgs on deploy. A second gated backfill (`repoint_default_evaluator_links_to_forks_v1`, `_backfill_repoint_default_links_to_forks`) then re-points existing links on the four **live** pivots (`test_evaluators`, `agent_evaluators`, `simulation_evaluators`, `annotation_task_evaluators`) from the shared template to the linking entity's org fork — re-pinning `evaluator_version_id` to the fork's live version on the two versioned pivots, soft-deleting a redundant template link when the parent already links the fork, and leaving a link on the template when the org deleted its fork. A third gated backfill (`repoint_default_evaluator_job_snapshots_v1`, `_backfill_repoint_default_job_snapshots`) then rewrites **finished-run** evaluator *references* from template to the run's-org fork, so a past run's evaluator click opens the fork. Two store shapes: JSON stores (`agent_test_jobs` / `simulation_jobs` / `jobs` `details`+`results`) get a per-row org-scoped **string-replace** of the unique 36-char `template_uuid → fork_uuid` token (no JSON parsing — the frozen prompt/rubric/scores are untouched, only the evaluator *identity* moves); column stores (`evaluator_runs`, `annotation_job_evaluators`) get an `evaluator_id` UPDATE (re-pinning `evaluator_version_id` where the column exists). Org is resolved per store (`agent_test_jobs→agents`, `simulation_jobs→simulations`, `jobs.org_uuid`, `evaluator_runs→jobs`, `annotation_job_evaluators→annotation_jobs→annotation_tasks`); a run whose org deleted its fork stays on the template. Verified on a prod copy: 601 references rewritten, 0 residual, idempotent. The templates still resolve by `slug` (`get_evaluator_by_slug`), so the STT/TTS "no evaluator selected" default fallbacks and the `default-llm-next-reply` synthetic-link / `test_evaluators` backfill are unchanged. The `owner_user_id IS NULL` immutability guard (`_owner_check` 403) still protects the templates, but an org can no longer discover a template uuid through the API.
- **Evaluators replace `metrics`**: the `metrics` table is frozen — new work goes to `evaluators` + `evaluator_versions`. Seeded defaults (`owner_user_id IS NULL`) are hidden templates that each org forks into an editable copy (see the per-org-fork bullet above). **All four flows (LLM tests, simulations, STT, TTS) resolve the evaluator's *current* live version at run time** — the pivots/snapshots still store a pinned `evaluator_version_id` (FK NOT NULL / snapshot carrier) but it's only a fallback for the degenerate deleted/no-live-version case. **LLM tests and simulations resolve live via a JOIN-through-live**: `get_evaluators_for_test` and `get_evaluators_for_simulation` JOIN the version columns through the evaluator's `live_version_id` (`COALESCE(e.live_version_id, te.evaluator_version_id)` / `COALESCE(e.live_version_id, se.evaluator_version_id)`, surfacing `ev.uuid` as the version id — same trick), so every run uses the latest evaluator prompt/rubric and editing an evaluator changes what already-linked tests/simulations use. **STT/TTS resolve live by re-hydrating at run time**: `_refresh_evaluators_to_live` (in [stt.py](src/routers/stt.py) / [tts.py](src/routers/tts.py)) re-reads each evaluator's `live_version_id` when the job executes and writes the refreshed snapshot back into job details before building the calibrate payload (submit-time `details.evaluators` snapshot kept as fallback if the evaluator was deleted/has no live version). Per-link/per-job `variable_values` stay pinned everywhere (they're config, not part of the version). Every finished run of all four flows still renders reproducibly because each snapshots the live-at-run-time version into its job (see Evaluator shape bullet). STT/TTS jobs store the same shape inside `details.evaluators` (no pivot table). `init_db()` seeds defaults with stable `slug`s, migrates legacy `metrics` rows into `evaluators` (marked via `source_metric_uuid`), and backfills LLM `tests` where `config.evaluation.type='response'` into a `test_evaluators` link against `default-llm-next-reply` with `variable_values={"criteria": <old text>}`. All three passes are idempotent — safe to rerun.
- **Evaluator shape**: `output_type` ("binary" | "rating") lives on the `evaluators` row — it's identity. The **rubric** (`output_config`, including scale values/labels/descriptions/colors) lives on each `evaluator_versions` row so prompt iterations carry their own pinned rubric. **LLM tests, simulations, AND STT/TTS all resolve the live version at run time** (see Evaluators-replace-metrics bullet — tests/simulations via the pivot JOIN-through-live, STT/TTS via run-time re-hydration), but each *finished* run snapshots the live-at-run-time rubric into its job (e.g. `evaluators_by_test_id` in [agent_tests.py](src/routers/agent_tests.py) for tests; `_snapshot_evaluators_for_job_details` for simulations; the refreshed `details.evaluators` for STT/TTS — all stored on the job and re-read via [utils.py](src/utils.py)), so the completed run's results still render against the exact rubric it used even after the evaluator is edited again. **Variables (`{{placeholder}}` names) are immutable across versions**: `create_evaluator_version` rejects (ValueError ⇒ 400) any new version whose variable *name set* differs from the prior version — only descriptions/defaults may change, and version 1 is unconstrained. This is load-bearing for the live-resolution path above for every flow that keeps pinned `variable_values` (LLM tests and simulations): the pivot pins `variable_values` but runs the live prompt, so if a later version could rename/add/remove a variable the pinned values would no longer fill the live placeholders, silently sending a half-rendered prompt to the judge. The frontend already forbids editing variables post-creation; this is the backend enforcement. **Versions are soft-deleted, never removed**: `DELETE /evaluators/{uuid}/versions/{version_uuid}` (JWT-only, like every other DELETE) sets `evaluator_versions.deleted_at` and refuses the live version (400) — the only guard needed, since every path that creates a version also sets it live, so the last surviving version is always the live one. The row survives so a finished run that pinned it still resolves its number and prompt — `get_evaluator_version`/`get_evaluator_versions_by_uuids` stay unfiltered by design, `get_evaluator_versions`/`get_evaluator_versions_for_evaluators` hide deleted rows (pass `include_deleted=True` for historical reads, as the annotation-agreement trend does), and `version_number` is never reused (`MAX(version_number)` counts deleted rows).
- **Evaluator type vs data type**: an evaluator carries **two independent classifying columns** on the `evaluators` row:
  - `evaluator_type` (`tts | stt | llm | llm-general | conversation`, default `llm`) — semantic category. `tts` judges TTS output; `stt` judges one transcript in isolation; `llm` judges one response with conversation history; `llm-general` judges a standalone, **non-conversational** `input → output` pair (generic LLM use cases); `conversation` judges a full conversation (used by simulations and `conversation`-type tests). The frontend filters per run context (`GET /evaluators?evaluator_type=stt` on the STT page, etc.). **This value was historically `simulation`**: `init_db()` runs an idempotent `UPDATE evaluators SET evaluator_type = 'conversation' WHERE evaluator_type = 'simulation'` migration. The same `simulation → conversation` rename was applied in lockstep to the annotation-task `type` and the default-prompt `purpose` so all three axes share one vocabulary — which `llm-general` also spans (evaluator_type, annotation-task `type` in `ANNOTATION_TASK_TYPES`, and default-prompt `purpose`). `ANNOTATION_TASK_TYPES` and `SUPPORTED_EVAL_TASK_TYPES` are identical (`stt | llm | llm-general | conversation | tts`) — every creatable task type has a wired evaluator-run path. **Tool call is NOT a task type; it is a per-row concern.** A single row inside a normal `llm`/`llm-general` task can carry a tool call as the agent's output instead of text — `is_tool_call_row(item)` in [utils.py](src/utils.py) detects it: an `expected_tool_calls` or `actual_tool_calls` **list present at all** (the shape an item built from a tool-call test or trace carries) makes it one whatever the agent produced, since an agent that answered in words and left the actual list empty is exactly the failure a person is there to mark; any other item qualifies only with no `agent_response`/`output` text AND a non-empty `tool_calls` list. `_TOOL_CALL_ITEM_CONDITION` in [db.py](src/db.py) mirrors this in SQL for the one-time tool-call-evaluator backfill's WHERE clause (it can't call the Python function per row there) and must move with it — `tests/test_db.py::test_tool_call_item_condition_matches_python_rule` checks the two agree. **`is_tool_call` is stamped once, at the DB layer, not per endpoint**: `db._parse_annotation_item_row` (used by both `get_annotation_item` and `get_annotation_items_for_task`) and `db.get_job_items` set it on every item dict they return, so it's on task detail, `GET /annotation-tasks/{uuid}/items`, single-item read, `task_summary`, and both public labelling routes automatically — no router-level helper to remember to call. An LLM judge can't score such a row, so `POST …/evaluator-runs` filters tool-call rows out of `items` before the run is created — they never enter `item_ids_persisted`, the item snapshot, or the item count — and 400s when nothing is left after that filter ("The chosen items evaluate one or more tool calls, which only supports human review today. Evaluators do not run on them."). This is a create-time filter, not a per-row skip: new runs never contain a tool-call row at all. Runs created before this filter shipped still carry one `evaluator_runs` row per (tool-call item × evaluator) with `{skipped: true, message: ...}`, written by the now-removed `_skip_runs_for_tool_call_rows`; those rows are frozen history the frontend still renders as "not judged", not something new runs produce. The `llm`/`llm-general` dataset builders still **skip** tool-call rows as a second line of defense — redundant against the new filter for a freshly submitted run, but still exercised by `_run_job`'s pre-snapshot backward-compat path (a job whose `annotation_eval_job_items` snapshot predates this filter). The frontend can only filter this way for an explicit row selection — it holds one page of rows, so "Evaluate all" and "select all across pages" (which send no row list) rely on the backend filter. A human labels a tool-call row through the ordinary annotation API — the verdict is the item's row-level annotation (`evaluator_id = NULL`) with `{value: bool, expected_tool_calls?: [...]}` (pass/fail under `value`, corrected calls alongside); A human labels a tool-call row against the shipped **`Tool call correctness`** evaluator (slug `default-tool-call-correctness`, `evaluator_type` `tool-call`, binary Correct/Wrong), so the verdict is an ordinary `(item, evaluator)` annotation and flows through every per-evaluator read path unchanged. That evaluator is human-answered only: its version carries an EMPTY `judge_model` and `system_prompt` on purpose (the columns stay `NOT NULL`, nothing rebuilds the table), and `_resolve_evaluator_dicts` in [annotation_eval_runner.py](src/annotation_eval_runner.py) drops any `tool-call` evaluator before the calibrate payload is built, raising when a request is made of nothing else. **The org's fork of it is protected** — a tool-call row has no other answer slot, so `DELETE /evaluators/{uuid}` 403s for it and `PUT /evaluators/{uuid}` 403s on `evaluator_type`/`data_type`/`kind`/`output_type` (`_LOCKED_UPDATE_FIELDS`), leaving name, description and the per-version rubric editable. Retyping it away from `tool-call` would be as damaging as deleting it, since `_resolve_evaluator_dicts` drops it from a calibrate payload BY TYPE and would otherwise send a judge with an empty model and prompt. Every evaluator response carries `is_protected` (true only for that one, keyed off `slug`/`source_default_slug` in `_is_protected`, so clients read one flag instead of special-casing the type). `db.delete_evaluator`/`db.update_evaluator` are unguarded, and the annotation code still tolerates a missing fork. `required_evaluator_ids_for_item(item, evaluator_ids, tool_call_evaluator_ids)` is the one rule both completion sites apply and the labelling form mirrors: a tool-call row needs ONLY the tool-call evaluator, every other row needs everything except it (the public job payload carries `is_tool_call` per item so the browser never re-derives it). `bulk_create_items` auto-links the org's fork the first time a tool-call row arrives; two one-time backfills (`provision_tool_call_evaluator_v1`, `link_tool_call_evaluator_to_tasks_v1`) ship it to existing orgs and tasks. **Agent-test runs snapshot it like any other evaluator**: a `tool_call` test links nothing and calibrate still computes `passed` by diffing the calls, but `_agent_test_job_details` freezes the org's evaluator into `details.tool_call_evaluator` at launch (`_tool_call_evaluator` in [agent_tests.py](src/routers/agent_tests.py)), and the run's `evaluators[]` entry, each row's synthesized `judge_results`, and the run-list name all read that frozen copy, so a later rename never rewrites a finished run. The frozen copy is the ONLY source: a run launched before it existed shows no evaluator entry and the literal `"Tool call"` in the list, and nothing re-resolves the evaluator at read time. The run-list name rides a dedicated `json_extract` column (`tool_call_evaluator_name`) alongside `has_tool_call_test`. The `evaluator_id=NULL` annotation slot now carries free-text comments only. For the annotation **eval-runner**, `tts` uses **`calibrate-agent tts --eval-only`**: items must carry `payload.text` + `payload.audio_path` (stored S3 key/URI, never a presigned URL); the runner downloads audio server-side via `download_file_from_s3`, materializes a run directory (`results.csv` + `audios/`), and judges the clip — same contract as the TTS benchmark eval. Results parse via the STT CSV path (`_parse_results_stt`). `llm-general` uses the dedicated **`calibrate general`** command (non-conversational `input → output` judge — no agent, no conversation, no `--eval-only` flag): `_build_llm_general_dataset` emits flat `{id, input, output, arguments?}` rows; the config is the **unrendered** evaluator payload (`build_evaluator_cli_payload_unrendered`, same as the `llm` task type) so `{{placeholder}}`s survive for per-row substitution. Per-item `evaluator_variables` use the **same payload contract as the `llm` task type** (`{evaluator_uuid: {var: value}}`) and are resolved per-evaluator the same way (`_criteria_refs_for_item`); `calibrate general` takes them as a per-row `arguments` object **keyed by evaluator name** (it renders each evaluator's prompt against `arguments[ev_name]`), exactly mirroring `llm`'s per-criteria `arguments` — each evaluator gets its own box, so two evaluators sharing a `{{var}}` name never collide. Item payload is `{input, output, evaluator_variables?}` (vs the `llm` task type's `{chat_history, agent_response, evaluator_variables?}`). Output is `results.csv` (same column-map shape as STT: `id` + `<name>`/`<name>_reasoning` per evaluator, mapped via `config.json`'s `evaluators_map`), so `_parse_results_general` delegates to the STT CSV parser verbatim.
  - `data_type` (`text | audio`, default `text`) — the medium the judge actually consumes. **This is the only field that says the judge consumes audio rather than text**, and it is passed straight through to the calibrate CLI in `build_evaluator_cli_payload()`, which does the routing.
  In practice `tts ⇒ data_type=audio` and the rest are `text`, but the split is preserved so a user can in principle define, e.g., a TTS evaluator that judges a transcribed text instead of audio without reclassifying its category.
  The schema went through an intermediate phase where `data_type` was renamed to `evaluator_type`; `init_db()` now runs both `ALTER TABLE evaluators RENAME COLUMN data_type TO evaluator_type` **and** `ALTER TABLE evaluators ADD COLUMN data_type TEXT NOT NULL DEFAULT 'text'` (both try/except guarded — fresh DBs and DBs already on the new schema both no-op). Then it remaps legacy `evaluator_type` values (`audio → tts`, `text → llm`) and backfills `data_type = 'audio' WHERE evaluator_type = 'tts' AND data_type = 'text'` so partially-migrated DBs land in the right place. `_seed_default_evaluators` then snaps each seeded slug to its canonical `(evaluator_type, data_type)` pair. Default seeds: `default-tts-audio-quality` → `(tts, audio)`; `default-stt-transcription` → `(stt, text)`; the seeded `conversation` evaluators (`default-sim-goal-completion`, `default-sim-empathy-tone`, `default-sim-persona-adherence`) → `(conversation, text)`; everything else (`default-llm-next-reply`, `default-faithfulness`, `default-helpfulness`, `default-safety`, `default-conciseness`, `default-instruction-following`) → `(llm, text)`.
- **output_config shape** — same entry form for every output type: `{value, name, description?, color?}`. Binary = 2-entry scale with bool `value`; rating = N≥2-entry with numeric `value`. Adding a new `output_type` (categorical, ranking, …) means a new JSON shape inside `output_config` — no schema change. `variables` also live per-version (they're defined by the prompt text).
- **Per-level rubric injection**: `_format_scale_rubric()` in [llm_judge.py](src/llm_judge.py) appends a `Rubric:\n  value (name): description\n...` block to the judge prompt whenever any scale entry has a `description`. Applied to the calibrate CLI payload (baked into the rendered `system_prompt` of each evaluator entry). Entries without a description are silently skipped — mixed-fill is fine.
- **API keys (`/api-keys`)** are credentials for programmatic API access, **scoped to one org**. The table stores a bcrypt `key_hash` plus the first-12-char `key_prefix` for candidate lookup; the raw `sk_…` key is returned exactly once at creation. After that, reads only ever expose `last_four` (the last 4 chars, stored in `key_last_four`) and a ready-to-render `masked_key` (`sk_••••<last_four>`) — never the prefix or hash. CRUD (`POST`/`GET`/`DELETE /api-keys`) is JWT-authed via `get_current_org`, so a key is minted in — and bound to — the caller's active org with the creator stamped as `owner_user_id` (revoke = soft delete). On the *consumption* side, `auth_utils.get_org_jwt_or_api_key` is a **required**-auth FastAPI dep that resolves an `OrgContext` from **either** a JWT (frontend) **or** an API key (any programmatic client): it accepts `X-API-Key: sk_…` or `Authorization: Bearer sk_…` (the `sk_` prefix lets keys coexist with JWTs in the same header), the key wins when present (owner role), it 401s on an invalid/revoked key, and otherwise falls back to `get_current_org` (401 if no JWT either). It's wired into the agent-test **run/poll** endpoints (`POST /agent-tests/agent/{uuid}/run`, `GET /agent-tests/run/{task_id}`) so both the FE and programmatic clients hit the same endpoints; ownership is enforced via `agent.org_uuid == ctx.org_uuid` (404 on mismatch). Benchmark + the rest of the agent-tests router stay JWT-only (`get_current_org`). One reference consumer is the GitHub Action in the separate `artpark/calibrate-github-action` repo (it hits `/agent-tests/agent/{uuid}/run` + `/agent-tests/run/{task_id}` with an `sk_` key).

The `evaluators` column reads two narrow `details` slices via SQL (`_AGENT_TEST_JOB_SUMMARY_COLUMNS` in db.py) — `evaluators_by_test_id` (uuid+name snapshot per test, from `_agent_test_job_details`) and a `has_tool_call_test` flag, **both snapshotted once at job-creation time** (not re-derived per list request) since a test's type and evaluator links are fixed for the life of the job. `_run_evaluator_names` then prefers each evaluator's *current* name over the frozen snapshot name (same preference order as `_build_evaluators_block_for_test_run`, via the same `_get_evaluator_cached_for_enrichment` cache) — the snapshot name is calibrate's disambiguated name (`Correctness-a1b2c3d4` when two linked evaluators share a display name) and goes stale on rename, so neither list-detail view should read it raw. Both route handlers seed `evaluator_cache` via `_prefetch_evaluator_cache(jobs)` — one batched `get_evaluators_by_uuids()` call over every evaluator uuid referenced across the whole job list (missing/deleted uuids cached as `None`) — before building any run item, so resolving names for a list of many runs costs one query total, not one per distinct evaluator. `has_tool_call_test` appends the literal `"Tool call"` as the last entry, since a tool-call test never carries an evaluator and would otherwise be invisible in this column. Empty list when the run had no evaluators. Jobs created before this feature shipped read `evaluators`/`has_tool_call_test` as empty/false (no historical backfill), same precedent as other snapshot-only fields. This exists because the full-detail list blew up the payload (many runs × full detail for each case × each model) and closed the MCP stdio connection. Keep list items slim — put any new per-case or per-model detail on the DETAIL endpoints, never back on the list.
- **Agent-test runners share one launch path.** `_launch_agent_test_run(agent, tests, s3_bucket)` snapshots the calibrate config + per-test evaluator metadata, creates the `llm-unit-test` job, and starts/queues the thread (returns `(task_id, status)`). Two endpoints use it: `POST /agent-tests/agent/{uuid}/run` (one agent, returns `AgentTestRunCreateResponse` — `task_id` + `status` only) and the batch `POST /agent-tests/run` (returns `{runs: [{agent_name, agent_uuid, task_id, status}], skipped: [...]}`). The batch endpoint's optional body drives scope: `{agent_names: [...]}` runs just those agents; omitted/null/empty runs **every agent in your workspace**. When names are given they're **validated up front** — any unknown name 404s with `{not_found: [...]}` and creates NO jobs. It fans out via `_run_tests_for_agents`, **one job per agent**, skipping-and-reporting agents with no linked tests or an unverified connection (`skipped` reason `no_linked_tests | connection_not_verified`) rather than failing the batch. The single-agent endpoint instead **400s** on those same conditions (`_agent_connection_unverified` is the shared guard). All launched jobs are subject to the normal per-org concurrency queue, so over-limit jobs come back `status="queued"`.
- **Calibrate CLI evaluator handoff** — the calibrate CLI accepts a minimal evaluator definition: `{name, system_prompt, judge_model, type ("binary"|"rating"), scale_min?, scale_max?}`. The backend's stored extras (`evaluator_type`, `data_type`, `kind`, `output_config.scale.{name,description,color}`) are NOT sent — they're either inferred by calibrate from the parent flow (e.g. TTS implies audio) or get baked into the prompt before sending (e.g. per-level `description`s become a "Rubric:" block via `_format_scale_rubric`). For STT/TTS the payload goes to `--config <path>` as `{"evaluators": [...]}`. For simulations it lives at `config.evaluators` (replacing the old `evaluation_criteria` key). For LLM tests/benchmarks the helper `build_test_evaluators_payload` produces a deduped top-level `evaluators` list (one entry per unique evaluator UUID — names suffixed with `-{uuid8}` on collision) and per-test-case `config.test_cases[].evaluation.criteria = [{name, arguments?}]` references; the top-level prompts keep `{{variable}}` placeholders unrendered so calibrate substitutes per test case using each criterion's `arguments`. STT/TTS/simulation payloads instead pre-render variables (no per-row arguments mechanism).
- **Four test types, one execution path — all run the agent live.** `tests.type` is one of `response`, `tool_call`, `conversation`, `general` (validated in [tests.py](src/routers/tests.py); `response`/`tool_call` pin `llm` evaluators, `conversation` pins `conversation` evaluators, `general` pins `llm-general` evaluators). `general` is the non-conversational counterpart of `response`: its config carries a plain `input` string instead of `history`, judged standalone with no conversation context. **Conversation and general tests require ≥1 evaluator** — enforced on single create/update AND bulk — because they have no fallback judge (unlike `response`, which can synthesize the default LLM judge from a legacy string `criteria`); without one a run would build an empty calibrate config with nothing to judge. **All four run through the same `calibrate llm` command** via `_build_calibrate_config` → `run_llm_test_task` ([agent_tests.py](src/routers/agent_tests.py)), and **all four invoke the agent** — `config.history` ends at the user turn the agent should answer (`general` has no `history`; `config.input` is the whole turn); calibrate runs the agent to produce its reply, then dispatches per test case on `evaluation.type`: `response`/`general` ⇒ judge only the generated reply; `conversation` ⇒ append the reply and judge the FULL conversation with the conversation judge; `tool_call` ⇒ diff the generated tool calls. Because the wire contract is identical, `_build_calibrate_config` treats `response`, `conversation`, and `general` the same: all three contribute to the deduped top-level `evaluators` list and get per-test-case `evaluation.criteria = [{name, arguments?}]` refs (via `build_test_evaluators_payload`); the evaluator payload is the same shape regardless of evaluator_type. Consequences: runs CAN mix types in one `calibrate llm` call; conversation tests benchmark meaningfully (the agent generates per model, so judgments differ); and the agent-connection-verified guard applies **uniformly** to every run (conversation tests call the agent too). Output (`results.json`/`metrics.json`) and the read-path enrichment + `evaluators[]` block builder are shared unchanged — `output.response` carries the generated reply, `judge_results` are keyed by evaluator name with `match` (binary) / `score` (rating), and per-test-case `passed` is computed **by calibrate** (AND across evaluators: binary must `match`, rating must equal `scale_max`), not by the backend. **Both runners store calibrate's RAW parsed rows at write time — never validate `judge_results` through a Pydantic model there.** calibrate emits `judge_results` as a *dict* keyed by evaluator name, but `TestCaseResult.judge_results` is typed `List[JudgeResult]`; the dict→list conversion happens only at READ time in `_enrich_test_results_with_evaluators` / `_enrich_model_results_with_evaluators`. `run_llm_test_task` (and the benchmark intermediate writer) already store plain dicts; `run_benchmark_task` must do the same — it builds plain dicts for `model_results` and lets the read endpoint reshape them (constructing a `ModelResult(...)` at write time raised `ValidationError` for any `response`/`conversation` test, since `tool_call` has `judge_results=None` and slipped through). The `BenchmarkStatusResponse`/`ModelResult` validation still runs — but at read time, after enrichment. **Perf metrics (latency + cost + total_tokens)**: calibrate reports per-run perf metrics for live runs. **Per-case location differs by depth (this is a deliberate calibrate asymmetry — do not "fix" it):** latency is **top-level** `result["latency_ms"]` (float ms — calibrate rounds internal-model latency, but external agent tests self-report it verbatim and may send a fraction, so `TestCaseResult.latency_ms` is `Optional[float]`); cost is **nested** `result["output"]["cost"]` (float USD). The aggregated `metrics.json` blocks: `latency_ms` is `{p50,p95,p99,count}` (calibrate switched latency to **percentiles** — `mean/min/max/std/values` are gone; `p50` is the closest equivalent to the old `mean`), while `cost` and `total_tokens` stay `{mean,min,max,count}` (`count` = how many cases actually reported a value, never zero-filled). The same percentile switch applies to the **STT/TTS `ttfb`** block (now `{p50,p95,p99,count}`) and the leaderboards (TTS `ttfb` column → `ttfb_p50/p95/p99`; LLM `latency_ms` column → `latency_p50/p95/p99`). The backend stays unaffected because it treats all these as opaque pass-through: latency/ttfb aggregates flow through as `Dict[str, Any]`, and the leaderboard readers (`read_leaderboard_xlsx`, `_read_leaderboard_csv`) are column-name-agnostic — so adapting to the percentile shape / renamed columns is the **frontend's** job. (Old pre-change result folders still hold `ttfb.mean`/`latency_ms.mean`; re-running a leaderboard over them silently drops the latency columns since the new reader looks for `p50` — re-run the eval or accept the missing column.) The backend reads aggregates **straight from calibrate's `metrics.json` (it does NOT recompute them from rows)** — if calibrate omits a block the aggregate is null even when per-case rows have values (that's a calibrate bug to fix CLI-side, not a backend fallback). For agent-connection (external) tests the agent self-reports via an optional `metrics: {cost, latency_ms, prompt_tokens, completion_tokens}` dict in its JSON reply (missing/malformed → skipped, not errored). `--provider openai` reports no cost (route via OpenRouter for cost). The backend threads them through: `_parse_agent_test_results` lifts `r["latency_ms"]` AND `output.cost` up onto each `TestCaseResult` (per-case; there is NO per-case `total_tokens` — it's aggregate-only); unit-test runs store the aggregates at `results.{latency_ms,cost,total_tokens}` (on `TestRunStatusResponse`/list items/public run); benchmark runs store them per-model on `ModelResult.{latency_ms,cost,total_tokens}` so the FE can compare models on all three (the leaderboard CSV carries `latency_ms`/`cost` mean columns via generic dict pass-through when calibrate writes the leaderboard). **All are omitted for eval-only runs / no-cost providers / when calibrate doesn't write the block** — every field is `Optional`/`None`-defaulting, so treat them as optional everywhere. **The immutable row `type` is the single source of truth for dispatch**, NOT the stored `config.evaluation.type`: `PUT /tests` keeps `type` fixed but accepts an arbitrary `config` dict, so the two can drift. `_build_calibrate_config` dispatches on the row `type` and **normalizes each test case's `evaluation.type` to it** before the CLI handoff, so a drifted config can never make calibrate judge the wrong way.
- **Shared list-endpoint deps live in [src/pagination.py](src/pagination.py).** Pieces: `PaginationParams` (FastAPI dep for `?limit=&offset=`, default `limit=50`, max `1_000_000`, `offset≥0` — cap is deliberately huge so FE "export all" flows can pass `limit=total` without a multi-request loop; the cap is a sanity guard, not a payload budget); `OptionalPaginationParams` (same but `limit` **defaults to `None` = no limit** — omitting the params returns every item) paired with the `PaginatedResponse[T]` generic envelope model (`{items, total, limit, offset}`, `total` = **pre-slice** count) and helpers `paginate(items, pagination)` (slice → envelope dict in one call), `count_and_page(items, pagination) → (page, total)` + `page_envelope(page, total, pagination)` (for endpoints that transform each item before wrapping — e.g. the slim-model projections `_to_agent_summary`/`to_test_list_response`/`_evaluator_response`, run only over the returned page); and three factories — `make_sort_params(sortable=[...], default=..., default_order="desc")`, `make_search_params(searchable=["payload.name", ...])`, and `make_projection_params(heavy_fields=[...])`. Each factory returns a fresh `Depends`-compatible class baked with that endpoint's allowlist; the class exposes `.apply(...)` (sort/search return a filtered/sorted copy; projection mutates+returns a dict). Per-endpoint usage: build the dep classes at module load (so FastAPI sees stable types and the factory's allowlist validation catches typos before request time), then `items = search.apply(items); items = sort.apply(items); return paginate(items, pagination)` (or `count_and_page`+`page_envelope` when the page needs a per-item transform). Sort's `apply()` defaults to `uuid` as a secondary key so identical-timestamp items don't shuffle across page boundaries (sqlite `CURRENT_TIMESTAMP` is second-resolution); pass `secondary_key="id"` for entities where bulk insertion is the common path (e.g. annotation items — `id` is the autoincrement and preserves insertion order, whereas `uuid` is random and would shuffle whole batches). Search standardizes on `?q=` (no per-endpoint name override) and case-insensitive substring; blank/whitespace is a no-op so FE inputs don't need clearing logic. Disallowed `sort_by` 422s at request time via manual `HTTPException` since `Literal` can't be built dynamically. Search/sort/paginate run **post-fetch in Python** — fine at current entity scale; push down into SQL inside the handler if a table outgrows that. Adopters: `GET /annotation-tasks/{uuid}/summary` uses `PaginationParams`+sort+search at the **item level** (each item explodes into ≥1 row per `evaluator × version`, `evaluators[]`/`annotators[]` blocks stable across pages) and inlines `pagination: {total, limit, offset}` in the body (its own composite shape, not the generic envelope). The **public list endpoints** — `GET /agents`, `/tests`, `/evaluators`, `/agent-tests/agent/{uuid}/tests` (name `?q=` search), `/annotation-tasks` (name `?q=`), and `/agent-tests/agent/{uuid}/runs` (`type`/`status`/`has_failures` filters, no name search — run names are auto-generated) — return `PaginatedResponse[T]` where `T` is the endpoint's **slim list model** (see the slim-summary-models bullet below); the slim projection runs only over the returned page. The JWT-only global `GET /agent-tests/runs` (workspace-wide, `get_current_org`) gets the **same** envelope + `type`/`status`/`has_failures` filters + paging — kept in lockstep with the per-agent runs endpoint so both read `.items`/`.total` identically. Both runs endpoints also accept `?around=<run_uuid>`: instead of the page at `offset`, `paginate_around()` (in [pagination.py](src/pagination.py)) returns the page containing that run (computed from its index in the filtered/sorted list and the effective `limit`, defaulting to `DEFAULT_LIMIT` when `limit` is omitted), 404 if the run isn't in the current filtered results — so a client that navigated away from a run into its detail view can reopen the list already scrolled to it. Search+filters run **before** the slice so `total` and the page reflect the filtered set. For the runs endpoints the per-run display names (`Run N`/`Benchmark N`) are assigned over the full ordered set **before** status/has_failures filtering, so a filter never renumbers them. **This envelope is a shape change from the historical bare-`List[...]`/`{runs}` responses — the web frontend reads `.items`/`.total`, and both runs endpoints return `.items` (not the old `.runs`).** Adding these params/shape does NOT touch routes, so the SDK overlays need no change (but the public spec's response schema changes, so clients regenerate on deploy). Other list endpoints (`/tools`, …) still return full bare lists — adopt `PaginatedResponse[T]`+`paginate` when adding pagination; don't invent a per-router shape. **Public DETAIL endpoints trim via `?compact=true` + per-endpoint filters, not slim models.** `make_projection_params(heavy_fields=[...])` builds a `compact: bool` dep whose `.apply(model.model_dump())` **nulls** the listed heavy fields *in place* (key kept, value → `None`) — so the wire shape stays `response_model`-compatible and the generated SDK/MCP types are unchanged; the weight shed is the values (transcripts, rubrics, prompts), not the key names. **Any field a projection nulls MUST be `Optional` on its model** (e.g. `EvaluatorVersionResponse.system_prompt`, `TaskSummaryResponse.item_comments` were relaxed to `Optional` solely for this) or `response_model` validation 500s. Path syntax per heavy field: plain key `"config"`, `[]` iterates a list (`"results[].output"`), `*` iterates a dict's values (`"rows[].annotations.*.reasoning"`); missing paths are silent no-ops. Adopters (all `tags=["Public API"]`, all handlers `model_dump()` → filter → `projection.apply()` → return dict): `GET /agent-tests/run/{task_id}` (`?only_failed` keeps `results` where `passed is False`; `?compact` drops `results[].{output,test_case,judge_results,reasoning}` + `evaluators[].output_config`), `GET /agent-tests/benchmark/{task_id}` (`?only_failed` narrows each model's `test_results`; `?compact` drops `model_results[].test_results` + rubrics), `GET /annotation-tasks/{uuid}/summary` (`?disagreement_only` filters at the **item** level *before* pagination — keeps items with ≥1 row where `evaluator_agreement` is set and `< 1`, so `pagination.total` reflects the disagreeing items and paging covers the whole set — then drops the agreeing rows within each surviving item; item- and row-level filters share one predicate (`_item_disagrees` mirrors the per-row agreement calc); `?compact` drops row payloads/reasoning + evaluator version bodies + `item_comments`), `GET /evaluators/{uuid}` (`?compact` drops `versions[].{system_prompt,output_config,variables}`). Like the list params, these add no routes → overlays untouched, but the public spec changes so clients regenerate on deploy. **`?compact` descriptions are auto-generated by the factory (list the dropped fields); hand-written filter `Query` descriptions must still pass `test_api_docs_style.py` — no nullability caveats (`| null` in the type already conveys it).**
- **List endpoints return slim summary models, not the full entity.** Several list/index endpoints deliberately return a trimmed shape distinct from their detail/full model, so heavy per-row fields stay detail-only (each is the `T` inside the `PaginatedResponse[T]` envelope from the pagination bullet above): `GET /agents` → `AgentSummary` `{uuid, name, type, updated_at, connection_verified}` (the full `config`, incl. credential-bearing `agent_headers`, is detail-only via `GET /agents/{uuid}` — never ship it in a bulk list); `GET /tests` **and** `GET /agent-tests/agent/{uuid}/tests` → a shared `TestListResponse` `{uuid, name, type, created_at, updated_at, config:{description}}` (defined in [tests.py](src/routers/tests.py) via `to_test_list_response()`, imported by [agent_tests.py](src/routers/agent_tests.py); drops `evaluators[]` and `config.history/evaluation/settings` — full shape on `GET /tests/{uuid}`, and note the projection deliberately **skips** the `get_evaluators_for_test` N+1); `GET /evaluators` → `EvaluatorResponse.live_version` is the slim `EvaluatorLiveVersionSummary` `{uuid, version_number, judge_model, variables}` (drops `system_prompt`/`output_config`; full version bodies live on `GET /evaluators/{uuid}` via `versions[]`). This mirrors the pre-existing `SimulationListResponse` vs `SimulationDetailResponse` split and the agent-test run-list index (`AgentTestRunListItem` + `TestRunCaseSummary`/`ModelRunSummary`, #121). **Rules:** never assume a list response carries the full entity — the frontend edit/detail views refetch `GET /{uuid}`; keep heavy or credential-bearing fields off list responses; and when the trimmed and full models diverge, add a *separate* list model rather than narrowing the shared `AgentResponse`/`TestResponse`/`EvaluatorResponse` (which POST/PUT/detail reuse). All four trimmed endpoints are `tags=["Public API"]`, so the overlays need no edit (no route add/remove/rename) but a trim re-publishes slimmer SDK/CLI/MCP models on next publish.
- **Default prompts API** — `GET /evaluators/default-prompt?purpose={llm|llm-general|stt|tts|conversation}` returns the canonical default system prompt + suggested config for prefilling the create-evaluator form. The same prompts power the seeded LLM/STT/TTS evaluators (built via `_seed_from_purpose` in [db.py](src/db.py) so `DEFAULT_PROMPTS_BY_PURPOSE` is the single source of truth). The `llm`, `llm-general`, and `conversation` purposes' prompts are templates with a literal `<ENTER EVALUATION CRITERIA HERE>` placeholder the user replaces directly (no `{{var}}`); the `llm`/`llm-general` *seeds* (`default-llm-next-reply`, `default-llm-general`) instead carry a real `{{criteria}}` variable. For `default-llm-next-reply` (the LLM-test flow) that variable substitutes per-test via calibrate `arguments`; for `default-llm-general` it substitutes per-item via `calibrate general`'s flat per-row `arguments` (fed from each annotation item's `evaluator_variables`), the same `{{var}}` mechanism. Default judge models: `DEFAULT_TEXT_JUDGE_MODEL` for text/STT/conversation/llm-general, `DEFAULT_AUDIO_JUDGE_MODEL` for TTS.

## Conventions

- **Comments are sparing by default** (full rule up top). Self-explanatory code carries no comment; a small change gets at most one short line; only a real footgun/tradeoff earns more. Don't narrate edits.
- New entities: UUID primary identifier (plus auto-increment `id`), `deleted_at` soft delete, `created_at`/`updated_at` timestamps, JSON `config` column for flexible fields, validated at the API layer via Pydantic.
- Many-to-many links use dedicated pivot tables with their own soft-delete column.
- When mutating child rows (e.g. `dataset_items`), bump the parent's `updated_at` in the same transaction.
- Schema migrations on existing tables: `ALTER TABLE ADD COLUMN` inside `init_db()`, wrapped in `try/except sqlite3.OperationalError: pass`. Use `DEFAULT NULL` — SQLite silently rejects non-constant defaults like `CURRENT_TIMESTAMP` in `ADD COLUMN`, and the `except` will swallow the failure.
- All job failures route through `capture_exception_to_sentry()` (marks as unhandled, flushes immediately — critical for background threads).
- CLI failure detection is two-layer: non-zero exit code **or** expected structured output missing. Never treat stderr content as a failure signal — the calibrate CLI emits benign cleanup tracebacks.
- **API `status`/`type` fields are concretely typed via shared enums/Literals in [utils.py](src/utils.py)** — never re-loosen a request/response model field to bare `str` when a closed value set exists. Two status vocabularies exist and must not be crossed: the **run family** (`TaskStatus`: `queued/in_progress/done/failed`, `cancelled` reserved; abort lives in `details.aborted`, not `status`) covers STT/TTS eval, agent-test, simulation, and annotation-eval jobs; the **annotation family** (`AnnotationStatus`: `pending/queued/in_progress/completed/failed`) covers labelling jobs and the public annotation-eval view, which normalizes the run family's internal `done` → `completed` via `_shape_eval_job_for_response`. Typing a response `status` with the *wrong* family (or omitting a value a writer can emit) turns an egress into a 500 via response-model validation — audit every write path before narrowing. Conversely, when a field can only hold a *subset* at a given lifecycle point, type it to that subset so the public docs advertise only the reachable values: **job-create responses** (`TaskCreateResponse`, `AgentTestRunCreateResponse`, `BatchTestRun`) use `InitialTaskStatus` (a two-value `queued`/`in_progress` Literal in utils.py), never the full `TaskStatus` — the launch path only ever emits those two. **Never re-list an enum's own values in a `Field(description=...)`** — the docs renderer (Mintlify) auto-lists them from the schema, so prose states purpose only (or glosses what each value *means*); a house-style convention documented in the `api-writing-style` skill. The `type`/`role` Literals (`SimulationRunType`, `AgentTestJobType`, `EvalJobType`, `AnnotationTaskTypeLiteral`, `TestTypeLiteral`, `EvaluatorTypeLiteral`, `MemberRoleLiteral`, …) **mirror DB constants/CHECKs** (`db.ANNOTATION_TASK_TYPES`, `db.VALID_EVALUATOR_TYPES`, `CHECK(role IN …)`) — Literals can't reference runtime tuples, so keep both in sync when the vocabulary changes. Tightening a request field means invalid input now 422s at the schema layer (not a hand-rolled 400) — update the matching test's asserted status code.
